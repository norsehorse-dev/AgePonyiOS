# AgePony

AgePony is an iOS app for file encryption and signing, built on
[age](https://age-encryption.org) and SSH. Everything happens on device — no
accounts, no servers, no tracking.

- **Encrypt / decrypt** files and text to age recipients (X25519, post-quantum
  `age1pq1`, the age 1.3 tag recipients `age1tag1` and `age1tagpq1`,
  `age1yubikey1`, ssh-ed25519, ssh-rsa) or with a passphrase (scrypt). Output is
  standard age, readable by the `age` CLI on macOS and Linux.
- **Hardware keys**: decryption keys made in the Secure Enclave and published as
  `age1tag1` or `age1tagpq1` recipients, which the `age` CLI 1.3 and later
  encrypts to with no plugin. YubiKey PIV slots decrypt over NFC.
- **Detached signing** via SSHSIG (`ssh-keygen -Y sign/verify` compatible),
  namespace `agepony`. Sign with an in-app SSH key, a Secure Enclave key, or an
  external **FIDO security key** over NFC — including PIN-protected keys
  (`sk-ssh-ed25519` and `sk-ecdsa-sha2-nistp256`).
- **Sign and encrypt** in one file that plain `age -d` still opens: the signature
  rides in an encrypted header stanza that `age` ignores.
- **Multi-file bundles**: pick several files and AgePony tars them into one
  `bundle.tar.age`.
- **Moving keys**: send keys to another phone (iPhone or Android) over local Wi-Fi,
  encrypted to a one-time post-quantum key, or print a paper backup that is itself
  a passphrase-protected age file.
- On-device vault behind Face ID or the device passcode, Face ID alone (no
  passcode fallback), or an AgePony password, with an optional duress password
  that wipes it. No telemetry (see
  `AgePony/PrivacyInfo.xcprivacy`). The only network request is the optional
  fetch of a GitHub user's public SSH keys.

## AgePonyCore

The cryptography lives in `Sources/AgePonyCore`, a dependency-free Swift package
(CryptoKit + Security + CommonCrypto). It has no UIKit or app dependencies and can
be reused on its own. It implements age, SSH key parsing, SSHSIG, the FIDO/CTAP2
and PIN-protocol stack, and a USTAR archiver, each pinned to reference vectors in
`Tests/AgePonyCoreTests`. The decrypt path also runs against all 147 vectors of the
C2SP CCTV age test suite (`Tests/AgePonyCoreTests/Testkit`); the few cases where
AgePony deliberately differs are listed with reasons in `RUNNER-NOTES.md` there.

### Post-quantum recipients

AgePonyCore implements the standardized post-quantum age recipient,
MLKEM768-X25519 — `age1pq1…` public keys and `mlkem768x25519` stanzas —
interoperable with the `age` CLI v1.3.0 and later.

On iOS 26 and macOS 26 the X-Wing and ML-KEM-768 steps run on CryptoKit
(`Crypto/HybridKEMBackend.swift`, `Crypto/CryptoKitPQ.swift`). AgePony's own
validation of stanzas and keys still runs first, and the MLKEM768-P256 combiner,
HPKE key schedule and SHA-3 stay AgePony's code, since CryptoKit has none of them.
Below iOS 26 neither half is available from Apple's frameworks, so both are
implemented from scratch:

| File | What it is |
| --- | --- |
| `Crypto/SHA3.swift` | Keccak-f[1600] sponge: SHA3-256/512 and the SHAKE XOFs. CryptoKit has no SHA-3. Squeezing is incremental, because ML-KEM's `SampleNTT` rejection-samples for an unbounded number of rounds. |
| `Crypto/MLKEM768.swift` | ML-KEM-768 (FIPS 203, final): NTT, K-PKE, implicit rejection. |
| `Crypto/HpkeMlkem768X25519.swift` | The X-Wing hybrid KEM plus RFC 9180 single-shot HPKE base mode. |
| `Stanzas/HybridStanza.swift` | `HybridRecipient` / `HybridIdentity`. |

The hybrid is "if either half holds, the file holds": breaking it requires both a
quantum computer for ML-KEM and a break of X25519. That is also why a post-quantum
recipient carries age's `postquantum` label — a file readable by an X25519 key is
only as quantum-safe as X25519, so AgePony refuses to mix the two rather than
silently downgrade the guarantee.

FIPS 203 *final* matters: it domain-separates key generation as `G(d ‖ k)`, which
the earlier IPD draft did not. The two derive different keys from the same seed.
The known-answer tests are pinned to vectors generated by `filippo.io/hpke`, the
implementation `age` itself uses, so a drift toward the draft fails loudly.

The app generates post-quantum identities, and files encrypted to them open with
standard `age`.

### Hardware recipients

`Stanzas/TagStanza.swift` implements the age 1.3 tag recipients: `age1tag1…`
(P-256, `p256tag` stanzas) and `age1tagpq1…` (ML-KEM-768 plus P-256,
`mlkem768p256tag` stanzas), with the P-256 HPKE half in `Crypto/HpkeP256.swift`.
The known-answer tests use the vectors from age's own `age-plugin-tagtest`.

In the app, the P-256 private key is generated in the Secure Enclave
(`Hardware/SecureEnclaveKeyAgreement.swift`) and can't be exported; the vault keeps
only the Enclave's opaque handle, which no other device can use. For `age1tagpq1`
keys made on iOS 26 or later, the ML-KEM-768 half is a Secure Enclave key as well
(`Hardware/SecureEnclaveMLKEM.swift`, `Hardware/SecureEnclaveTagPQ.swift`), so
neither half can leave the phone. Keys made before 5.1.0 or below iOS 26 keep the
ML-KEM-768 seed in the encrypted vault. Hardware identities are left out of key transfer and paper
backups, so they stay on the phone that made them.

`PIV/` and `Stanzas/YubiKeyIdentity.swift` decrypt files encrypted to a YubiKey PIV
slot (`piv-p256` from age-plugin-yubikey, and `p256tag`) over NFC.

### Bounded memory

Every format AgePony handles has a streaming path that holds a fixed working
buffer regardless of file size, so a 1 GB file behaves like a 1 KB one:

- `Age.encryptStream` / `decryptStream`, and the chunked payload underneath
- `AgeArmorStream.swift` — an armor encoding sink and a decoding source that
  substitutes for an `InputStream`
- `Archive/TarArchiveStream.swift` — tar in both directions: push (`writeEntry`)
  and pull (`source`), because encrypt reads its plaintext from a stream while
  decrypt writes to one
- `Signing/SSHSigHashStream.swift` — incremental message hashing, so a large file
  can be signed without being held
- `Age.parseHeaderStream` / `canDecryptStream` — a header-only probe that reports
  what a file is encrypted to, and whether you hold a key for it, without
  decrypting; instant at any file size

Each streaming path is tested for byte-identical output against its whole-buffer
counterpart, so the two cannot drift.

### Signatures

For public-key recipients, sign-and-encrypt puts the SSHSIG in an extra
`agepony.com/sig` header stanza (`Signing/SignatureStanza.swift`), encrypted under
a key derived from the file key. Plain `age` ignores the stanza and returns the
original file, and only someone who can open the file can see who signed it.
Version 2 signs the plaintext hash together with every other stanza in the header,
so a recipient can't re-address the file to someone else and keep it showing as
signed.

age requires an scrypt stanza to stand alone, so passphrase files keep
`Archive/SignedBundle.swift`: a small USTAR container with the payload and its
SSHSIG, age-encrypted as a unit. Its version 2 signature also covers the file name.
Files signed with version 1 of either format still verify. Files signed on Android
5.0.1 verify here and the other way round.

`SignedBundleUnwrappingSink` strips the container mid-stream while hashing the
payload in passing, and passes anything that is not a bundle straight through, so
the decrypt path can route every output through one code path.

## Build

Open `AgePony.xcodeproj` in Xcode and build the `AgePony` scheme (iOS 17.0 or later). Set
your own team under Signing & Capabilities — `DEVELOPMENT_TEAM` in the committed
project is NorseHorse's and will not match yours. The NFC security-key feature
needs the Near Field Communication Tag Reading capability and a real device; NFC
is not available in the simulator.

Run the crypto tests:

    swift test
